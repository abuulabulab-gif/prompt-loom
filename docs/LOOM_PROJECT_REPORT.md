# LOOM Project Report — v0.9 Beta
**作成日:** 2026-05-23  
**URL:** prompt-loom.com  
**用途:** このドキュメントはClaudeやGeminiなどのAIへ現状共有・今後の相談に使用する

---

## 1. アプリ概要

LOOMは、AIイラスト生成ツール（Midjourney・NovelAI・Stable Diffusion・Flux・DALL-E等）向けの**プロンプトをタグ単位でビジュアルに管理・構築するブラウザPWAアプリ**。  
外部サーバーへの送信は一切なく、全データはブラウザのIndexedDB（Dexie）にローカル保存される。

**技術スタック:** Vite + React 18 + Tailwind CSS + Dexie (IndexedDB) + PWA (@vite-pwa)  
**対応環境:** PC・スマホ、ダーク/ライトテーマ、日本語/英語切替

## 4. IndexedDBの制約と現状の課題

### 4-1. デバイス間での同期は不可（現状）
IndexedDBは「ドメイン × ブラウザ × デバイス」ごとに完全独立。
PCとスマホのデータは自動では同期されない。手動JSON書き出し→読み込みで移行可能。

### 4-2. デバイス買い替え時
IndexedDBはブラウザのローカルデータ。買い替え時はデータが消える。
→ 現状の対策: JSON書き出しで手動バックアップのみ。

### 4-3. ストレージ容量
| ブラウザ | 上限の目安 |
|---|---|
| Chrome (PC) | ディスク空き容量の60% |
| Firefox | ディスク空き容量の50% |
| Safari (Mac) | 1GB前後 |
| **iOS Safari** | **最大1GB、7日間未使用でデータ消去リスクあり**（PWAインストール済みなら保持） |

### 4-4. 画像容量の管理
- v0.9でCanvas圧縮（長辺600px・WebP 72%）により1枚あたり50〜80KB程度に抑制
- 最大4枚/キャラ × 100キャラ = 約20〜32MB（現実的な範囲）
- EXIF回転（iOSで撮影した縦写真）は未対応（既知の制約）

## 6. v2.0実現のための課題と大変な点（AI向け補足）

> この項目は、v2.0検討時にAIへ相談するための前提情報として記載する

### 6-1. バックエンド導入（★★★ 最も大変）
- 現状は完全なフロントエンドアプリ（サーバーレス）
- クラウド同期にはユーザー認証（メール/Google OAuth等）が必要
- IndexedDBのデータ構造をそのままAPI経由で扱うには設計変更が伴う
- **具体的に大変な点:**
  - ユーザーごとのデータ分離（Row Level Security等）
  - オフライン→オンライン復帰時のコンフリクト解決（複数デバイスで同時編集した場合）
  - 画像データ（base64 blob）をDBに入れるかストレージ（S3等）に分けるか
  - 無料枠での運用コスト設計（Supabaseは500MBまで無料）

### 6-2. マルチデバイス同期のコンフリクト問題
- スマホで編集しながら、PCでも同時に別の変更をした場合の「どちらが正しいか」問題
- Last-Write-Wins（最後の書き込みが勝つ）が最も実装が簡単だが、一方の変更が消えるリスクがある
- CRDTやOperational Transformationは実装コストが非常に高い
- **現実的な解決策の候補:**
  - デバイスごとにバージョン番号を管理し、古いほうがマージを促すダイアログを表示
  - スマホはReadOnlyで、PCでのみ編集を許可するなど役割分担

### 6-3. 画像ストレージの設計
- base64をDBに入れると1キャラ最大約400KB→大量キャラで数十MBがDB直行
- S3/Supabase Storageに分ける場合、アップロードAPIの設計が別途必要
- CDNキャッシュと組み合わせることで読み込み高速化は可能

### 6-4. AI提案タグ機能
- OpenAI API等をフロントエンドから直接叩く場合、APIキーがブラウザに露出するリスク
- バックエンドのProxy経由でAPIを叩く設計が安全だが、バックエンドが必要になる
- ユーザー自身のAPIキーを登録してもらい、クライアントサイドで直接呼ぶ方式は技術的には可能（Anthropic/OpenAIはCORSを許可している）だが、セキュリティ上の懸念をユーザーに説明する必要がある
